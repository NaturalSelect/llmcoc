# 业务流程设计

本文档补齐项目的业务流程设计。现有项目说明集中在 `README.md`，其中功能概览、API 路由、启动与初始化行为是本文件的主要依据；实现细节参考 `cmd/server/main.go`、`internal/handlers`、`internal/models` 和 `internal/services`。

## 业务边界

LLM-COC 是一个房间制 COC7 在线跑团服务。核心用户是玩家和管理员：

- 玩家注册登录后创建调查员，进入房间，按回合提交行动，与 AI KP 跑团。
- 管理员维护用户、邀请码、公告、商店、模组、LLM Provider、Agent 配置和规则缓存。
- 系统负责持久化角色、房间、消息、模组、经济和 Agent 运行所需状态。

## 启动与初始化流程

服务启动入口是 `cmd/server/main.go`，流程如下：

1. 读取 `CONFIG_PATH` 指向的配置文件，默认使用 `config.yaml`。
2. 初始化 SQLite 数据库，开启 WAL 和外键，并通过 GORM 自动迁移模型。
3. 首次启动时从 `scenarios/` 导入内置模组。
4. 写入默认商店商品。
5. 根据环境变量初始化默认 LLM Provider，并补齐 Agent 配置。
6. 加载 `COC_kp.md`、`COC_spell.md`、`COC_monster.md`，供规则顾问和规则缓存使用。
7. 注册 `/api` 接口和内嵌前端静态资源。

相关说明见 `README.md` 的“默认数据与初始化行为”和“环境变量”。

## 账号与权限流程

注册登录流程：

1. 前端登录页调用 `/api/auth/settings/public` 获取是否需要邀请码。
2. 用户注册时，如果站点设置要求邀请码，后端校验邀请码是否存在且未使用。
3. 注册成功后创建普通用户，发放初始金币和人物卡槽位。
4. 登录成功后返回 JWT，前端存入 `localStorage`。
5. 后续接口通过 `Authorization: Bearer <token>` 鉴权。

权限流程：

- 普通用户可以管理自己的人物卡、进入房间、购买商品、发送行动。
- 管理员通过管理后台维护用户、模组、商城、Provider、Agent、系统设置和规则缓存。
- 项目不会自动创建管理员；README 说明了首次使用时通过 SQLite 修改用户角色。

## 人物卡流程

人物卡是玩家进入游戏的身份载体：

1. 玩家可以创建、编辑、删除人物卡，也可以调用 AI 生成人物卡。
2. 人物卡包含 COC 属性、衍生属性、技能、背包、法术、社会关系、已见神话存在、疯狂状态和伤亡状态。背包和账号仓库里的物品是结构化的 `{name, desc, count, type}`，`type` 取 `equipment`/`weapon`/`accessory`/`tome`/`artifact`/`misc`/`story`；名称和描述都相同的物品合并成一堆并累加数量，商城重复购买、仓库存取、KP 发放都遵循这条规则。仓库存取可以只转移部分数量，存取期间人物卡不能在进行中的房间里。`story` 是剧情物品，只能由 KP 在对局中通过 `manage_inventory(add)` 发放，不与同名同描述的普通物品合并（两者不能并存，KP 需换描述），不能存入仓库，手动添加物品的接口也会拒绝；房间结算（`RunEndSession`，含 `end_game`、手动结束和管理员批量结束）时不论胜负和生死都整件收回，并给每件发一条玩家可见的移除事件。
3. 创建和生成流程会补齐基础属性、HP、MP、SAN、技能等数据。
4. 游戏中 Agent 通过工具修改人物卡状态，例如 HP、SAN、MP、背包、法术、关系、位置和护甲。社交关系分两层：本局新增/更新/移除先记录在房间会话里（tier1），不占用人物卡空间；结算时由 AI 判断哪些关系值得长期写入人物卡（tier2），人物卡已有关系的更新/移除则直接生效，不需要 AI 判断。
5. 死亡角色进入阵亡列表，玩家可按规则消耗金币复活或彻底删除。

主要实现位于 `internal/handlers/character.go`、`internal/services/game` 和 `internal/services/agent/editor.go`。

## 模组流程

模组是房间运行的剧本来源：

1. 启动时如果数据库没有模组，系统从 `scenarios/` 导入 JSON 模组。
2. 管理员可以创建、上传、删除模组，也可以下载 JSON 模板。
3. 管理员可以调用 AI 生成模组，后端异步运行 Scripter 团队，生成完成后写入数据库。
4. 模组内容包含背景、开场、地图、场景、NPC、线索、胜利条件、失败条件和奖励。
5. 前端跑团大厅和创建房间流程读取可用模组列表。
6. 管理员可以在后台「线上模组」浏览 cnmods 的公开列表，点「下载」由服务端解析蓝奏云分享页、下载压缩包、提取 docx / pdf / txt / md 正文并存档。自动下载失败（例如被 CDN 挑战拦截）时，条目标记为失败，管理员在自己的浏览器里下载后上传同一条记录，走同一套提取流程。rar / 7z 不支持。
7. 提取时会对正文做「禁止投喂 AI」类声明的正则筛查。命中的文档默认不能编译，管理员读过原文后可以放行，放行人和时间会记录；重新下载或重新上传会清空放行。编译由管理员手动触发，复用「上传故事编译模组」的编译流水线（进度仍以 SSE 推送），入库后回填线上模组的 `scenario_id`，作者写成 cnmods 上的原作者。
8. cnmods 上的模组多数不可商用、禁止二改二传，只用于本站跑团，不要对外分发。编译出的模组默认对所有玩家可见，站点对外开放时由管理员自行把握。

主要实现位于 `internal/handlers/scenario.go`、`internal/models/scenario_module.go` 和 `internal/services/agent/scripter*.go`；线上模组见 `internal/handlers/online_module.go`、`internal/models/online_module.go` 和 `internal/services/onlinemod`。

## 房间与跑团流程

房间是一次跑团的运行容器：

1. 玩家选择模组创建房间，可设置最大玩家数和房间密码。
2. 其他玩家选择自己的人物卡加入房间；一张人物卡同一时间只能参与一个未结束房间。
3. 房主开始游戏后，房间状态从 `lobby` 变为 `playing`，系统把发言权交给 KP（`Spotlight` 写入空状态）。
4. 前端进入游戏页后先建立房间 WebSocket（`GET /sessions/:id/ws`），连上后拉取房间详情、消息记录和 chat-status 作为快照，之后所有进展都由推送驱动，没有定时刷新；房主端随即调用 `POST /sessions/:id/kp-turn`，由 KP 先手跑开场段，不等玩家发言。
5. 整局由 KP 驱动，发言权只有两种状态（`Spotlight` 为 NULL 的旧房间不再兼容，按 KP 持有处理）：
   - KP 持有发言权：没有任何玩家可以发言，提交会被拒绝（409）并提示「KP 正在推进剧情」。如果上一个周期被强制结束（`Spotlight.Stop` 非空），提示改为「KP 已暂停，请等待房主让 KP 继续」。
   - KP 点名了一位调查员（`ask_players` 一次只能点一个人，多人回应要分多次点）：只有被点名者可以提交，其他人被拒绝（403）并提示「KP 正在等待 X 回应：问题」。被点名者提交后才开始下一个周期。
6. KP 的一次发言权周期（floor）是一次 ReAct 循环：KP 可以反复调用工具，一个周期里可以产生多条叙事、多张配图、多条回复，没有续跑次数上限。只有 `ask_players`（点名并交出发言权）和 `end_game` 会正常结束周期；`narrate` 只发布一条 KP 消息，周期继续。
7. 周期也可能被强制结束，发言权回到 KP 并记录原因，等房主继续：
   - `host_stop`：房主或管理员调用 `POST /sessions/:id/kp-stop` 打断。
   - `loop`：同一批工具调用在滑动窗口内重复过多（第 3 次提醒，第 5 次中止）。
   - `stall`：连续多轮没有产生任何玩家可见消息。
   - `error`：LLM 调用或消息发布失败，或服务关闭。
   - `context`：上下文过长。这一种服务端会先总结再自动续跑一次；续跑仍没有产出才转为暂停。
8. 房主或管理员可以随时调用 `kp-turn` 让 KP 继续：未回应的被点名者会被跳过，已提交的声明仍会交给 KP。
9. `/chat`、`/kp-turn`、`/kp-stop` 都立即返回 202。KP 的全部进展通过房间 WebSocket（`GET /sessions/:id/ws`）广播给每个在线的人，事件与断线重连规则见 `docs/realtime-protocol.md`。
10. 战斗和追逐中，DEX 顺序只是建议，KP 可以点名任何还没行动的参与者；PC 必须先提交声明才能结算。
11. Agent 的每次产出落成独立消息：Writer 叙事（`writer`）、KP 回复（`kp`）、点名（`ask`），带 `kind`、`status`、`floor`、`meta` 字段。writer 先以 `pending` 落库并广播，异步补全后变 `done` 或 `failed`。配图由 Writer 在写正文时调用 `paint` 工具完成：工具立即返回占位地址 `illust://<n>`，Writer 把它写成 markdown 图片放进正文，图片在后台并发绘制，画完（或失败）后写进这条消息的 `meta.illustrations` 并广播 `illustration` 事件，前端在占位处显示“配图生成中”，画完替换成图片，失败的不显示；点名和 KP 叙事不等配图。旧对局里已有的独立 `image` 消息照常显示，新对局不再产生。Writer 按会话排队依次生成；KP 只发 write 的那一轮不等它，但之后要发布 KP 回复或点名时，会先等已发布的 Writer 全部写完，保证玩家先读到叙事再被提问。kp-stop 会立刻结束这次等待，已发布的 Writer 消息仍会写完。客户端断线后，服务端仍会跑完周期并落库。
12. 房主或管理员可结束游戏；结束时扣除金币，只发基础奖励并恢复角色状态，没有评分和成长。KP 通过 `end_game` 自然结束时在 `settlement` 里给每位调查员评分并报告用过的技能，金币按评分折算，胜利时对报告的技能做成长检定。
13. 管理员可以复活已结束房间，系统写入复活系统消息。

主要实现位于 `internal/handlers/session.go`，前端对应 `frontend/src/game/roomController.ts` 和 `frontend/src/game/roomState.ts`。

## Agent 跑团流程

Agent 管线负责把玩家行动转成规则裁定、状态变化和叙事输出：

1. ChatStream 或 KPTurn 构造 `GameContext`，启动一个周期。玩家回应周期带当前输入、多人待处理行动和 KP 上一次的提问；KP 主动周期（开场、房主继续、上下文总结后续跑）不带玩家输入，改带 `KPFloor`（`opening` / `host_continue` / `resume`）。
2. Director 读取剧本、当前状态和玩家行动（KP 主动周期读取 `<kp_floor>`），输出 JSON 工具调用数组。
3. 后端按工具注册表执行工具，工具结果作为下一轮输入返回给 Director。每轮结束后，本轮产生的玩家可见内容立刻发布为消息并保存转录检查点，不必等周期结束。
4. Lawyer 只负责查 COC 规则、法术和怪物资料，并可使用规则缓存。
5. NPC Agent 负责临时 NPC 的行动和对话，并维护独立记忆。
6. Writer 看到 Director 在发布这一轮时的完整消息链（含此前已完成 write 的正文），再收到一条按 direction 续写的指令，生成玩家可见正文；Writer 没有独立历史。
7. Director 调用 `ask_players` 或 `end_game` 后，周期结束。`ask_players` 把发言权交给被点名的调查员，周期因其他原因被强制结束时发言权回到 KP 并记录原因。服务端据此更新 `Spotlight` 后才广播 `spotlight` 与 `floor_end`。
8. 防循环：同一批工具调用在最近 10 轮内重复出现，第 3 次给 KP 追加提醒，第 5 次中止周期；只读调用的重复结果走缓存，跨轮的重复结算会被去重。
9. 上下文压缩只有一级：LLM 总结。历史单元原样累积，周期开始前或周期中途上下文逼近窗口时，把较早的拍总结成最前面的一个摘要单元。切点只落在拍的边界上，当前周期的内容永远不被总结；周期中途总结完会继续同一个周期。
10. NPC 状态、线索、位置、背包、伤亡、疯狂等状态按各自模型持久化。

重点边界：

- LLM API 推送给后端的是模型输出或工具调用 JSON。
- 后端给前端推送的实时进展是房间 WebSocket 事件，命令接口只返回 202。
- Writer 叙事正文和 KP 直接回复在前端用不同样式展示。

主要实现位于 `internal/services/agent/orchestrator.go`、`internal/services/agent/actions.go`、`internal/services/agent/director.go`、`internal/services/agent/writer.go`、`internal/services/agent/lawyer.go` 和 `internal/services/agent/npc.go`。

## 商城与经济流程

商城提供人物卡槽、装备、武器和配件等商品：

1. 系统启动时写入默认商品。
2. 玩家在商城浏览商品并购买。
3. 购买成功后扣除金币，写入交易记录，并按商品类型更新用户或人物卡。
4. 管理员可以创建和删除商品。
5. 管理员可以给用户充值金币。
6. 结束游戏时每名玩家消耗固定金币，并触发结算流程。结算发放的奖励金币：基础 20，其余由 KP 的评分决定（评分/2），手动结束没有评分。
7. 创建房间时房主可以勾选「通关后改写存活调查员的个人经历」（默认关闭，创建后不可修改）。开启后，胜利结算会让 AI 依据本局记录给每位存活调查员的个人经历追加长期影响，改写不可撤销；失败、阵亡的调查员和手动结束不会触发。结算的金币、技能成长、数值恢复、疯狂解除和经历改写都会作为结算事件显示在房间里。

主要实现位于 `internal/handlers/shop.go`、`internal/handlers/admin.go` 和 `internal/handlers/session.go`。

## 管理后台流程

管理后台是现有控制面，前端位于 `frontend/src/views/admin/`（路由 `/admin/:tab`，每个 tab 一个组件）：

1. 用户管理：查看用户、充值、切换管理员、封号和解封。
2. LLM Provider：创建、编辑、删除、Ping 测试。
3. Agent 配置：绑定 Provider、设置模型、token、温度、推理强度和启用状态。
4. 模组管理：查看、删除、上传、下载模板、AI 生成。
5. 商城管理：创建和删除商品。
6. 系统设置：控制注册是否需要邀请码。
7. 邀请码管理：批量生成、查看和删除未使用邀请码。
8. 公告管理：创建、编辑、下线、删除首页公告，支持置顶、级别和有效期。
9. 规则缓存：查看命中统计和清空缓存。

新增后台能力时优先扩展这个页面和现有 `/api/admin` 路由。

## 数据与状态设计

项目以 SQLite 作为唯一业务数据库：

- 用户、人物卡、模组、房间、房间玩家、消息、商城、交易、Provider、Agent 配置、系统设置、邀请码、公告都由 GORM 模型管理。
- 剧本内容、角色属性、技能、背包、法术、关系、战斗状态、追逐状态等复杂结构使用 JSON 字段存储。
- 规则资料来自仓库内 Markdown 文件，不存入数据库。
- Lawyer 规则缓存默认持久化到 `data/lawyer_cache.json`，并通过规则文件哈希判断是否可复用。

## 变更影响检查

修改业务流程时至少检查这些位置：

- API 是否需要更新 README 的路由概览。
- 前端是否需要同步更新 `frontend/src`（页面在 `views/`，后台 tab 在 `views/admin/`，实时房间逻辑在 `game/`）。
- 数据模型是否需要兼容旧 JSON 字段或旧数据库行。
- Agent 工具是否需要更新 Director 提示词、工具结构、工具执行器和测试。
- 多人回合逻辑是否会影响等待、断线重连和消息持久化。
- 规则、骰子、伤亡、理智、成长等机制是否需要引用规则资料或补测试。
